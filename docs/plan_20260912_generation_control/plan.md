# Light Plan: 音楽優先の生成リソース制御

2026-09-12 / Tier: Light / worklog: enabled / E2E: 対象外 / 実装未着手。

## 目的と範囲

Irodori v4.1 使用時、VRAM 12GB 環境で音声と音楽の同時生成がほぼ停止するという利用者報告に対応する。第1段階で生成を直列化し、待機中の音楽を優先する。第2段階で未再生 BGM を2曲先読みし、Talk が遅れたときは準備済み BGM で進行を続ける。ジャンル変更は再生中の曲を保ち、次に選ぶ BGM へ反映する。

- **第1段階・必須**: 共通実行枠、音楽優先、同期取得と先読みの経路統合、取消・失敗・Shutdown の整合。
- **第2段階・低優先度だが今回の実装対象**: 2曲の先読み、Talk 待ちの BGM 継続、ジャンル切替時の無効化、fallback とファイル保持の整合。第1段階の独立受入後に進める。
- **対象外**: 実サービス/実 GPU/実 UI の E2E、速度・VRAMの数値改善目標、VRAM自動監視、モデル軽量化/常駐化、複数アプリ間の排他、外部 LLM の GPU 利用制御、開始済み推論への割り込み、新規依存・外部 API・設定 UI。
- 既存プロセス内の `generation`、サービス、Player を局所変更するため Light とする。新規計画作成は利用者指定。完了済み移行計画と旧連番計画は改変しない。

## 現行の根拠

[調査メモ](../cheatsheet/generation-scheduling.md)に確認箇所と検証結果を集約。`generation.Queue` / `MaxWorkers` は生成経路で未使用。TTS の mutex は音声サービス内だけで、音楽のロード/推論/Close とは排他されない。`Player` と `App.PrefetchTalk` は Talk→Music の順に別 goroutine を起動する。音楽先読みは1件で、Talk が未完成だと同期生成を重ねる。ジャンル変更は先読みを保持し、fallback はジャンルを識別せず現在のラベルを付ける。

## 実装方針

### 第1段階: 共通枠と優先順（REQ-01〜03）

- `internal/generation` にプロセス共有の調停を置く。容量は1固定、music/talk の待機列を持ち、解放時は有効な music→talk、同種 FIFO で選ぶ。`maxWorkers` 設定や provider によってこの排他を解除しない。テストには独立した調停インスタンスを注入可能にする。
- `musicgen.Service.Generate` と `localtts.Service.synthesizeWav` の Runtime ロード直前から Close 完了までを枠の対象にする。TTS は文間も1 Talk 全体を保持する。RSS/LLM、モデルをロードしない事前検査、生成済み WAV の再生・取得は枠の外。既存の TTS mutex と共通枠の取得順を統一し、取消確認をロード直前にも行う。
- 「同時」は、調停が次の処理を選ぶ時点で両方が受付済み、または同じアプリの先読み契機で両方を要求する場合。同一契機は Player 側で music 予約を同期登録してから Talk を起動する。予約を context 内の内部情報として Service に渡し、Service は一度だけ消費する。直接 Service を呼ぶ経路は自分で予約する。単なる goroutine 起動順や sleep に依存させず、未消費予約も取消・早期失敗時に必ず解除する。
- 予約の取消は実行前なら待機列から外す。実行後は既存の実 worker join と Runtime Close が完了するまで枠を保持する。`defer` の順序を Close→解放とし、失敗経路でも漏らさない。稼働中の音声を追い越すための中断・再ロードは行わない。
- Player は同じ Talk/BGM 需要について同期取得と先読みで処理・結果を共有する。音声準備の LLM 呼出も重複させない。待機は `p.mu` の外で行い、Player 終了時は予約取消→worker join→既存 ORT Shutdown の順。結果公開には世代＋owner を照合し、完了処理は owner が自分の予約だけを解放する。Skip による世代変更後も予約が永久に busy にならず、旧 worker が置換 owner を消さないよう既存テストを更新する。
- 現在の要求期限（同期 Music 90秒/Talk 180秒、先読み Music 180秒/Talk 240秒）は待機込みで維持する。期限切れは既存エラー処理へ渡し、無制限延長・即時の無限再試行を加えない。既存 status の busy は受付～実終了を表し、両方 busy でも同時推論とは扱わない。

### 第2段階: 2曲先読みとジャンル世代（REQ-04〜07）

- `prefetchedMusic *Result` を容量2の FIFO と不足分の予約管理へ置き換える。1曲完成ごとに公開し、不足分を逐次補充する。消費で空きができたら補充し、ready＋予約が2なら追加しない。キャッシュをGPUモデル/テンソルの常駐とはしない。
- `NextItem` は Talk が必要かつ ready なら Talk、未完成ならその Talk を1件だけ開始/継続して ready BGM を選ぶ。Talk 待ちの代替 BGM では Talk の順番を消費せず、完成後の次の境界で採用する。BGM も空なら共有 BGM 処理を待つため、キャッシュ枯渇時の無停止は保証しない。Talk 失敗時は従来の slot 消費/BGM fallback とし、空回りする再試行を避ける。
- 音楽専用 `musicEpoch` を追加する。ジャンル正規化後に値が変わった場合、FIFO を空にし、旧音楽予約を取消し、新 epoch の補充を開始する。全体の `generation` をジャンル専用変更で進めず、Talk/現在の曲を維持する。Settings 保存でジャンルだけが変わった場合も同じ経路を使用する。
- 音楽 worker は設定 snapshot・epoch・owner を持つ。取消できない旧実推論は join/Close を待ち、結果を公開せず、自身が作った未公開 WAV/metadata のみを片付ける。成功/失敗による status 更新、fallback、FIFO への追加、`RegisterFile` 前後の最終選択でも epoch を確認する。変更と競合した取得は最新 epoch で選び直し、通常のジャンル変更だけで再生をエラー停止させない。A→B→A でも古い A worker の結果を復活させない。
- 「次のトラック」は変更適用後に Player が選択確定する次の BGM。既に返却済みの現在 item、Talk と gap は中断しない。新ジャンルが未生成なら待機があり得る。キャッシュ破棄は先読み/旧予約の無効化であり、出力フォルダ全体の一括削除は行わない。
- 新規 WAV に生成時ジャンルを保存する sidecar metadata を付け、fallback ではその値を検証する。既存の metadata なし WAV は残すが候補から外す。無効化された旧 worker の出力も候補外。ジャンル一致を確認できる保存済み WAV の再利用は可能だが、現在の選択値でラベルを上書きしない。
- `CacheLimit` はディスク保存数、2曲は未再生先読み数として区別する。共有の参照保護で生成完了→FIFO→選択→audio URL の受渡し中にも削除の隙間を作らず、`TrimCache` は保護中の path を飛ばす。保護数が上限を上回る間は削除を延期し、解放/URL失効後の整理で上限へ戻す。sidecar も対応する WAV と一緒に整理する。
